# Каркас агента сверки

Агент отвечает на вопросы о сверке начислений за месяц. Модель может запросить
вызов только инструмента из явного списка `AgentTools`; сам вызов выполняет код
приложения. Источником фактов служит существующий `ReconciliationService`.

```text
Пользователь → агент → проверка аргументов → read-only инструменты
                                          → ReconciliationService
                                          → 1С + PostgreSQL
             ← структурированный результат ←
             ← объяснение с периодом, итогом и расхождениями
```

## Границы ответственности

- `source/agent/tools.py` — операции объявлены через `@tool` из `langchain-core`.
  `AgentTools` хранит явный список разрешённых операций, проверяет аргументы и
  отклоняет неизвестные имена. Схема вызова модели берётся из того же объявления.
- `source/agent/dependencies.py` — создаёт инструменты только при наличии
  `AGENT_DATABASE_URL`; подключение импортёра не используется.
- `source/agent/routerai.py` — адаптер выбранной модели; он передаёт модели
  описание единственного инструмента, а фактический вызов проводит через
  `AgentTools`.
- `source/services/reconciliation_service.py` — единственный сценарий сверки для
  HTTP API, CLI и агента.
- `source/domain/reconciliation.py` — детерминированные правила сравнения и подсчёта.
- `source/repositories/` и `source/clients/onec_client.py` — чтение данных из
  PostgreSQL и 1С.
- `source/services/import_service.py` — отдельный сценарий записи; агенту он не
  предоставляется.

## Разрешённые инструменты

1. `read_onec_charges(period)` — прочитать начисления из read-only HTTP-источника
   за месяц в формате `YYYY-MM`.
2. `read_postgres_charges(period)` — прочитать начисления из PostgreSQL за месяц
   через отдельное подключение с правами только на чтение.
3. `reconcile_charges(period)` — выполнить сверку этих данных и вернуть
   структурированный отчёт.

Другие инструменты добавляются только под конкретный вопрос пользователя и с
отдельной проверкой необходимости. Инструментов изменения 1С или PostgreSQL нет.

CLI-агент может вызывать каждый инструмент отдельной командой:

```bash
uv run --env-file .env python -m source.cli.agent_tools read_onec_charges --period 2026-08
uv run --env-file .env python -m source.cli.agent_tools read_postgres_charges --period 2026-08
uv run --env-file .env python -m source.cli.agent_tools reconcile_charges --period 2026-08
```

Каждая команда печатает JSON. `period` проверяется до чтения; произвольный SQL и
команды записи отсутствуют. Сейчас проверен локальный mock-источник. Подтверждение
работы с опубликованной настоящей 1С остаётся отдельным интеграционным шагом.

## Правила реализации

- Аргументы инструментов валидируются до обращения к источникам.
- Инструменты возвращают типизированный JSON с периодом, статусом, итогами и
  расхождениями. Текст ответа модели не считается источником данных.
- Ошибка или недоступность 1С передаётся как ошибка; она не трактуется как
  пустой список или успешная сверка.
- Агент использует `AGENT_DATABASE_URL` с отдельными учётными данными PostgreSQL,
  имеющими права только на чтение. Пароль импортёра в его окружение не передаётся.
- Лимиты вызовов модели и инструментов, тайм-ауты и журнал технических ошибок
  настраиваются отдельно от бизнес-логики.
- Ключ модели берётся из переменной окружения и не попадает в репозиторий или логи.

## Проверка по шагам

1. Вызвать инструменты без модели и сравнить результат с HTTP API и CLI.
2. Проверить `MATCH`, `MISMATCH`, неверный период и недоступность 1С.
3. Проверить отказ записи под учётной записью агента.
4. Подключить выбранную модель и проверить, что её ответ опирается на результат
   инструмента и не придумывает суммы или причины расхождений.

Для локального запуска нужны `LLM_API`, `AGENT_DATABASE_URL` и адрес источника
`SOURCE_BASE_URL` или `ONEC_BASE_URL` в игнорируемом Git файле `.env`:

```bash
uv run --env-file .env python -m source.agent.cli "Сверь начисления за 2026-08"
```

Живой тест требует работающего HTTP-источника и PostgreSQL. Без вызова инструмента
адаптер не сообщает факты о данных и просит указать период.

Веб-чат использует тот же адаптер через `POST /api/agent/chat`. Сервер проверяет
месяц из формы, последовательно вызывает только read-only инструменты
`reconcile_charges` и `summarize_payments`, затем передаёт их результаты модели
для объяснения. Модель не выбирает SQL или действие. История чата хранится
только в открытой вкладке браузера.
